## Findings

### #1 [P2] Adding a whole-line comment changes how compact settings bind [Withdrawn]

- **Status** Withdrawn. See the triage note at the end of this finding.
- **Location** `source/Domore.Conf/Conf/Text/Parsing/TokenParser.cs:69-84`.
- The parser chooses newline separation as soon as the raw input contains a line feed. It then skips recognized comments, but keeps the separator chosen before skipping them. Adding a comment above or below a single line of semicolon-separated assignments changes the first value and drops the subsequent settings.
- Compact text is an existing output format of `ConfText(multiline: false)`, with semicolon-separated settings covered by `tests/Domore.Conf.Tests/Conf/Extensions/ConfObjectTest.cs:58-65`. The new comments documentation describes comment lines as ignored (`source/Domore.Conf/README.md:60-74`).
- Reproduced through `Conf.Contain(source).Lookup` on the reviewed .NET Framework 4.8 assembly with `Conf.Comment = "//"`.

  | Source as a C# string literal | Value of A | Value of B | Pair count |
  | --- | --- | --- | --- |
  | `"A = 1; B = 2"` | `1` | `2` | 2 |
  | `"// explanation\nA = 1; B = 2"` | `1; B = 2` | Absent | 1 |
  | `"A = 1; B = 2\r\n// explanation"` | `1; B = 2` | Absent | 1 |
  | `"// explanation\nA = 1\nB = 2"` | `1` | `2` | 2 |

- The baseline already chooses the grammar from the presence of a raw line feed. The defect is in composing that rule with the newly supported comment syntax. A string setting can silently absorb later settings, and a typed setting can fail conversion.
- **Suggested resolution** Preserve compact parsing when recognized comment lines are the only extra lines. Keep the existing treatment of literal semicolons in newline-separated settings and the existing preservation of comment markers inside multiline values. Verify that adding leading and trailing comments with LF or CRLF preserves the pairs from a compact serialization.
- **Triage (withdrawn)** The reproduction is accurate, but the behavior is not caused by comment support. Any source containing a line feed is parsed with newline separators, and semicolons in it are literal value text; a comment line is simply a line. Reproduced through `ConfFrom` against the net10.0 build of `d299f85c97fbcfb5f9ad778d0c292f7256203c1f`:

  | Source as a C# string literal | `Conf.Comment` | Value of A | Value of B |
  | --- | --- | --- | --- |
  | `"A = 1; B = 2"` | `"//"` | `1` | `2` |
  | `"// x\nA = 1; B = 2"` | `"//"` | `1; B = 2` | Default |
  | `"Conn = c\nA = 1; B = 2"` | `null` | `1; B = 2` | Default |
  | `"// db\nConn = Server=x;Database=y"` | `"//"` | Default | Default; `Conn` is `Server=x;Database=y` |

  The third row shows that a setting line has the same effect with comments disabled, so comment lines are consistent with the established grammar. The fourth row shows why the suggested resolution is harmful: if comment-only extra lines restored semicolon separation, adding a header comment to a file would split connection strings and other values containing semicolons. An optional README sentence could state that multi-line sources, including those whose extra lines are comments, treat semicolons as literal text. No code change is planned.

### #2 [P3] Static configuration can use two comment markers in one bind

- **Status** Accepted; not fixing. See the triage note at the end of this finding.
- **Location** `source/Domore.Conf/Conf/Converters/ConfTextAttribute.cs:20-27`.
- Static `Conf.Configure<T>(factory)` uses the shared mutable container. `ConfContainer` parses and groups the outer pairs before invoking the factory (`source/Domore.Conf/Conf/ConfContainer.cs:120-130`). A factory can set `Conf.Comment` while creating an object. The in-flight operation retains the old outer pairs, and the nested `[ConfText]` conversion then reads the new marker from the same container. The resulting object silently retains the initial value of any nested property whose setting matches the new marker.
- Reproduced on the reviewed .NET Framework 4.8 assembly using `Conf.Source = "Settings[item].Child = {\nText = expected\n}"`, an initial marker of `"#"`, and a `Settings.Child` property marked `[ConfText]` with `Child.Text` initially set to `"original"`. Static configuration bound `"expected"` with an ordinary factory and returned `"original"` when the factory assigned `Conf.Comment = "Text"`. A container created with `Conf.Contain` bound `"expected"` with the same marker-changing factory. The reproduction runs on one thread.
- This affects the static container. The independent container case fixed by issue #1 in `agents/reviews/2026-11-12_Review-001.md` still passes. The baseline had no configurable marker, so its nested parsing could not change this way.
- **Suggested resolution** Carry the marker used to parse the outer content into the converter state for that bind. Verify that an in-flight static bind uses its original marker for nested values and that a subsequent static bind uses the marker set by the factory.
- **Triage (accepted; not fixing)** Confirmed against the net10.0 build of `d299f85c97fbcfb5f9ad778d0c292f7256203c1f`: an ordinary factory bound `expected`, and a factory assigning `Conf.Comment = "Text"` bound `original`. Because the static `Configure` overload enumerates lazily, the trigger is slightly broader than reported: changing `Conf.Comment` in the consuming `foreach` body after the first item also affects later items (two items bound `expected`, then `original`). In every case, the caller must change the global marker while a static bind on the same container is still in progress, which is comparable to mutating a collection during enumeration. This differs from issue #1 in `agents/reviews/2026-11-12_Review-001.md`, where a container created earlier must stay independent of later global changes, a normal usage pattern that remains covered. The suggested resolution would need to thread the marker through the four internal `ConfPopulator.Populate` call sites in `ConfContainer` and into `ConfValueConverterState`. That would add no public API, but it adds plumbing across the bind path for caller misuse, so the issue is accepted without a fix. Reopen it if consistency under mid-bind marker changes becomes a supported requirement.
