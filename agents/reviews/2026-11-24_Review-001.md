## Findings

### #1 [P3] Lone carriage return inside a value starts a comment and drops the setting [Resolved]

- Status: Resolved
- Location: `source/Domore.Conf/Conf/Text/Parsing/TokenParser.cs:13` and `source/Domore.Conf/Conf/Text/Parsing/TokenParser.cs:79-87` (target revision).
- Problem and trigger: `StartsComment` treats any position after `'\r'` as the start of a line, but the parser's separator is `'\n'` (or `';'` when the source has no `'\n'`). A carriage return that is not followed by `'\n'` therefore lies inside the current single-line value from the parser's perspective. When comments are enabled and such a `'\r'` is followed by optional whitespace and the marker, the loop at lines 79-87 skips to the next line break and replaces the in-progress `SingleLineValueBuilder` with a new `KeyBuilder`, discarding the pending key and value. Reachable with sources that contain mixed line endings or embedded carriage returns, and with CR-only sources.
- Impact: The affected setting silently keeps its previous or default value, with no error. This contradicts the documented contract in `source/Domore.Conf/README.md:72-74` and `source/Domore.Conf/Conf/Conf.cs:50-53` that only lines beginning with the marker are comments and that markers within values remain literal text. With comments disabled, the same source binds the value.
- Evidence: Reproduced through the public `ConfFrom` API against the freshly built net10.0 `Domore.Conf.dll`, using a type with string properties `A` and `B` defaulting to `default`:

  | Source | `Conf.Comment = null` | `Conf.Comment = "#"` |
  | --- | --- | --- |
  | `"A = x\r#y\nB = 2"` | `A = x#y`, `B = 2` | `A = default`, `B = 2` |
  | `"A = 1\r# c\rB = 2"` (CR-only) | `A = 1# cB = 2`, `B = default` | `A = default`, `B = 2` |
  | `"A = 1\r\n# c\r\nB = 2"` (control) | `A = 1`, `B = 2` | `A = 1`, `B = 2` |

  The CR-only row was already mis-parsed with comments disabled, so it is a related symptom of the same root cause rather than a separate regression. Existing tests in `tests/Domore.Conf.Tests/Conf/ConfContainerTest.cs:1300-1313` cover only `"\n"` and `"\r\n"` line endings.
- Suggested resolution: Recognize a line start only at index 0 or immediately after the parser's separator (`'\n'` in multiline sources; CRLF is still covered because `'\n'` follows `'\r'`). Optionally, also require the current token to be a fresh `KeyBuilder` so that comment detection can never discard an in-progress value.
- Verification: Add `ConfContainerTest` cases with comments enabled asserting that `"A = x\r#y\nB = 2"` binds `A` to the same value as with comments disabled, and that existing LF/CRLF comment cases still pass.
- Resolution: Comment handling in `source/Domore.Conf/Conf/Text/Parsing/TokenParser.cs` now uses `'\n'` as its only line boundary, matching the parser's multiline separator. `StartsComment` recognizes a line start only at index 0 or after `'\n'` (line 13), its leading-whitespace scan stops only at `'\n'` (lines 17 and 29), and the comment-skip loop in `Pairs` consumes through to the next `'\n'` (lines 81-84). CRLF sources are unaffected because `'\n'` follows `'\r'`. The same root cause also ended a comment at a lone `'\r'`, letting text after it on the same line parse as a setting; that symptom is corrected by the skip-loop change and covered below.
- Fix verification:
  - Added `MarkersAfterALoneCarriageReturnRemainLiteral` (3 cases: lone CR mid-value followed by LF, by CRLF, and at end of a `';'`-separated source) and `LoneCarriageReturnDoesNotEndAComment` (LF and CRLF) to `tests/Domore.Conf.Tests/Conf/ConfContainerTest.cs`. Against the unfixed parser on net10.0 all 5 failed for the reported defect: the setting kept `original`, or text after the lone CR inside a comment bound `also ignored`. After the fix all 5 pass.
  - Rebuilding the scratch reproduction above against the fixed assembly yields identical results with comments enabled and disabled for both the lone-CR and CR-only sources; the CRLF control, indented CRLF comments, and a leading marker in a `';'`-separated source behave as before.
  - `dotnet build domore-conf.slnx --configuration Release -p:ArtifactsPath=F:/dev/me/domore-conf/out/review-002`: 0 warnings, 0 errors.
  - `dotnet test --no-build --no-restore --configuration Release` with the same `ArtifactsPath`: `Domore.Conf.Tests` net8.0 and net10.0 Passed 403/403 each; net48 and net462 Passed 389, Skipped 14, Failed 0 each. `Domore.Conf.Cli.Tests` net8.0 and net10.0 Passed 97/97 each.
