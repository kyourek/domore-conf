## Findings

### #1 [P2] Preserve the originating container's comment setting during nested conversion [Resolved]

- Status: Resolved
- Location: `source/Domore.Conf/Conf/Extensions/ConfObject.cs:36` (target revision).
- Problem and trigger: The new assignment reads the current global `Conf.Comment` every time `ConfFrom` is called. `[ConfText]` conversion calls this method internally (`source/Domore.Conf/Conf/Converters/ConfTextAttribute.cs:20`) instead of using the originating container's captured setting. Create a container while comments use `#`, change the global marker to `Text`, then configure an object whose `[ConfText]` property contains `Text = expected`. The outer container still uses `#`, but the nested conversion silently treats the setting as a comment. This contradicts the documented inheritance-at-creation behavior and the independence that the new container tests establish.
- Impact: Previously created containers can produce different nested objects solely because another caller changes the global setting. Nested settings are silently omitted even though the original container does not classify them as comments.
- Evidence: An in-memory reproduction against the freshly built target's .NET Framework 4.8 assembly returned `original` from the following sequence; the expected result is `expected`. `Parent.Child` has `[ConfText]` and is initialized to a `Child` whose public string `Text` property defaults to `original`.

  ```csharp
  Conf.Comment = "#";
  var container = Conf.Contain("Child = {\nText = expected\n}");
  Conf.Comment = "Text";
  var actual = container.Configure(new Parent(), key: "").Child.Text;
  // actual == "original"
  ```

- Suggested resolution: Carry the originating container's comment setting into nested `[ConfText]` conversion. Keep global inheritance for newly initiated public `ConfFrom` operations, while making nested conversion use the existing operation's setting.
- Resolution: Added an internal `ConfFrom` overload that accepts an explicit comment marker. Existing entry points still inherit `Conf.Comment`; `[ConfText]` now supplies the marker captured by its originating container.
- Verification: `NestedConfTextUsesTheCommentMarkerCapturedByItsContainer` failed for both marker-change directions before the fix and passed 2/2 afterward. The complete core test suites passed on net8.0 and net10.0; see post-fix validation below.

### #2 [P2] Keep comment filtering out of synthesized CLI configuration [Resolved]

- Status: Resolved
- Location: `source/Domore.Conf/Conf/Extensions/ConfObject.cs:36` (target revision).
- Problem and trigger: `CliProvider.Conf` converts parsed command-line tokens into generated conf lines and calls this internal overload (`source/Domore.Conf.Cli/Conf/Cli/CliProvider.cs:46-50`). Applying `Conf.Comment` here allows a valid option name to turn its generated assignment into a whole-line comment. For example, with marker `text`, `text=expected` is discarded, whereas `Text=expected` binds successfully. CLI documentation explicitly promises case-insensitive option names; neither command contains a user-authored comment line.
- Impact: An explicitly supplied CLI argument can silently retain its old/default value. A `[CliRequired]` property does not protect against this: `TargetDescription.Conf` removes the option from its required list before the generated conf is subsequently filtered. Thus the call reports success even when that required property was never populated.
- Evidence: An in-memory reproduction against the freshly built target's .NET Framework 4.8 core and CLI assemblies produced `original` and `expected`, respectively, for the following inputs. `Command.Text` is a public string property with `[CliRequired]`, initialized to `original`.

  ```csharp
  Conf.Comment = "text";
  var cli = new CliProvider(new CliSetup());
  var lower = cli.Configure(new Command(), "text=expected").Text;
  var upper = cli.Configure(new Command(), "Text=expected").Text;
  // lower == "original"; upper == "expected"; neither throws
  ```

- Suggested resolution: Disable comment interpretation for the CLI's generated conf, or bind its parsed pairs without reparsing them as user text. Keep the documented global setting for public text configuration operations.
- Resolution: `CliProvider` now parses synthesized configuration with comments explicitly disabled. Nested `[ConfText]` conversions inherit that disabled setting. The CLI README documents this behavior.
- Verification: `Configure_BindsNamedRequiredOptionWhenItMatchesCommentMarker`, `Configure_BindsPositionalRequiredArgumentWhenItMatchesCommentMarker`, `Configure_ThrowsForInvalidNamedRequiredValueWhenItMatchesCommentMarker`, and `Configure_DisablesCommentsForNestedConfTextAfterGlobalMarkerChanges` failed before the fix and passed afterward. `Configure_ThrowsWhenRequiredPositionalArgumentIsMissingWithMatchingCommentMarker` preserved the existing required-option error. The complete CLI suites passed on net8.0 and net10.0; see post-fix validation below.
